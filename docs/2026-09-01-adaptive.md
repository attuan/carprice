# 信頼度ルーティングをライブラリにした（`AdaptivePredictor`）

2026-09-01 / `unfold/adaptive.py`・`tests/test_adaptive.py`・`scripts/run_adaptive.py`

## 何のためにやったか

設計書（`dialogs/unfold-landing.html`）の3本柱のうち、**機能A（`Feature`）と
機能B（`LLMPredictor`）はライブラリになっていたが、信頼度ルーティングだけが
なっていなかった。** 8/31 までの P4 で「どの信号で選ぶと良いか」は測ってあった
（`scripts/find_routing_signal.py`）が、それは**測定済みの行データを後から
並べ替えて曲線を引くスクリプト**であって、利用者が使える API ではない。

そこを埋めた。加えて、これが必要である理由は数字で言える。機能B は
**1行につき1回 LLM を呼ぶ**ので、行数がそのまま費用と時間になる。
実測値（1行 $0.0086 / 並列8で 1.03 秒）を Craigslist の 6 万行に当てると

    60,000 行 × $0.0086 = 約 $516 、 60,000 行 × 1.03 秒 = 約 17 時間

となり、そのままでは回せない。**どの行を LLM に回すかを絞る仕組みが無いと、
機能B は小さな実験でしか使えない。**

## 何を作ったか

`AdaptivePredictor` は機能B を包んで、「LLM を呼ぶ前に手に入る信号」だけで
呼ぶ行を選ぶ。呼ばなかった行は統計モデル（既定では LightGBM）が答える。

```python
from unfold import AdaptivePredictor

model = AdaptivePredictor(target="価格_usd", unit="USD",
                          numeric=["車齢", "走行距離_mile"],
                          categorical=["メーカー", "州"], text="車種名",
                          escalate_rate=0.3)      # 信号の強い上位3割だけ回す
model.fit(train)
model.plan(test)        # 呼ぶ前に「何行・いくら・何秒」（LLM を呼ばないので無料）
pred = model.predict(test)
model.report()          # 何行回して、いくらかかったか
model.route()           # 行ごとにどちらの経路を通ったか
model.curve(test)       # 割合を振ったときの精度・費用・レイテンシ
model.review_queue()    # LLM が答えた行 = 教師ラベル候補
model.approve()         # 承認すると次回はその行を呼ばずに返る
```

設計書と PRD §6.3 が要求していたのは次の4点で、いずれも入っている。

| 要求 | 対応 |
|---|---|
| 閾値ひとつで「全行呼ぶ」と「1行も呼ばない」の間を連続に動かせる | `escalate_rate=0.0〜1.0`（`threshold` でも切れる） |
| 精度・レイテンシ・費用が同時に見える | `curve()` が3列を1つの表で返す |
| 答えは教師ラベル候補としてキューされ、承認すると高速パスが広がる | `review_queue()` → `approve()` |
| 基準は confidence だけではない（新車種・新グレードが絶えず入る） | `signal="unseen"` を用意。自作の信号も渡せる |

### 選べる信号

**LLM を呼ぶ前に手に入るものだけ**を信号にしている。P4 で最良だった
「LLM が動かした量」は、呼んでからでないと分からないので費用の節約には使えない。

- `disagreement`（既定）… LightGBM と XGBoost の予測の開き。**統計モデル自身が
  迷っている行**に回す。8/31 の測定で最良だった信号
- `similarity` … 近傍1位の類似度が低い行。渡せる証拠そのものが弱い行
- `unseen` … 訓練データに無いカテゴリ水準・未知語を含む行
- 自作 … `f(X, evidence) -> 配列` を渡す（大きいほど回す）

### 承認は行番号ではなく中身で照合する

`approve()` した答えは、行の内容から作った指紋（sha1 の先頭16文字）で覚える。
次回の `predict` で行の順番や件数が変わっていても効く。

## 実測（Craigslist・fold1 の 60 行・上位30%）

```
.venv/bin/python scripts/run_adaptive.py --dataset vehicles --no-curve --n-eval 60 --rate 0.3
```

| | 行数 | 採用した値の MAE | LightGBM 単体の MAE |
|---|---:|---:|---:|
| LLM に回した行 | 18 | **3,394.22** | 4,362.84 |
| 高速パスの行 | 42 | 2,082.85 | 2,082.85 |
| 全体 | 60 | **2,476.26** | 2,766.85 |

MAE（平均絶対誤差＝予測が平均で何ドルずれるか）で読む。

- **回した18行で LLM は LightGBM より 969 USD 良かった。** 選んだ行が
  実際に「LLM の判断が効く行」だったということ
- **全体では 2,767 → 2,476 と 291 USD 改善した。費用は $0.155。**
  1台あたり 0.26 セントで 291 USD 精度が上がった勘定になる
- 高速パスの行の誤差（2,083）が LLM に回した行（3,394）より小さいのは当然で、
  **難しい行を選んで回している**からである。ここを「ルーティングが効いている
  証拠」として読んではいけない。見るべきは**同じ行の上での比較**（上の表の左右）

承認の動作も確認した。18行を `approve()` したあと同じ60行をもう一度予測すると、
**LLM 呼び出しは 0 回**で、来歴の由来は `{'model': 42, 'human': 18}` になる。

### 費用

この検証にかかった実費は **$0.19**（18行 × 1回 + 手戻り3行）。
2回目以降はディスクキャッシュが効いて $0.00 だった。

## 副産物: 整形済みデータの再現性を直した

検証の途中で、**8/31 までの測定を無料で再現できないことが分かった。**
`sampledata/processed/vehicles_multi_clean.parquet` を作り直したところ、
`load_dataset(sample=60_000)` が引く 6 万行が当時と別物になり、
プロンプトが変わって LLM のキャッシュが1件も当たらなかった。

原因は `scripts/clean_vehicles.py` の書き出しに順序指定が無かったこと。
DuckDB は並列に読むので、**同じ入力・同じ SQL でも行の並びが実行ごとに変わる。**
残る行の集合は決まっている（`row_number() ... ORDER BY id` で決めている）が、
並びが変われば位置で引く `df.sample(n=60_000, random_state=SEED)` の結果も変わる。

`COPY (SELECT * FROM clean ORDER BY 物件ID) TO ...` に直した。
**以後は同じ行が出るので、再実行は無料になる。**

ただし **8/31 までの Craigslist の測定値は、そのままでは再現できない。**
当時の parquet が残っていないためで、リーダーボードの値と厳密に比べたい場合は
測り直しが要る（600行の曲線で約 $5）。傾向を見るぶんには当時の値が使える。

## 残っていること

- **600行での曲線を引き直す。** `run_adaptive.py --dataset vehicles`（`--n-eval 120`）で
  約 $5。8/31 の測定（30%で 2,767 / 75%で 2,479）と同じ形になるかを見る
- **シエンタでは信号が効かなかった**（`results/routing_signals.csv`）。
  単一車種では LLM の判断が効く余地そのものが小さいためで、
  `curve()` を自分のデータで引いて確かめてから使う、という手順にしてある
- 機能A（`Feature`）側にも confidence によるエスカレーションがあるが、
  こちらとは別実装になっている。共通化するかは未判断
