## 0. 用語（この文書で使うもの）

初めて出てくるものだけ、ここでまとめて定義する。

| 用語 | 意味 |
|---|---|
| **MAE**（平均絶対誤差） | 予測が平均で何万円ずれるか。小さいほど良い。価格の中央値が 185.7 万円なので、MAE 13 は約 7% の誤差にあたる |
| **フューショット学習** | LLM に「入力 → 正解」の例を数件プロンプトに貼り、そのパターンを真似させるやり方。ここでは「この車はこういう説明文で、実際は 180 万円でした」を5件見せる |
| **5-fold 交差検証** | データを5つに分け、4つで学習して1つで採点することを5回繰り返す。全データが1度ずつ採点側に回る |
| **アブレーション** | 部品を1つ外して測り、その部品が効いていたかを確かめる実験 |
| **オラクル** | 「正解を知っていれば選べたはずの最良」。実現不可能だが、伸びしろの上限を測る基準になる |

## 1. 何を作ったか

設計書（`dialogs/unfold-landing.html`）の **機能B（Capability B）** を実装した。
仕組みは、8/31 のミーティングで伊藤さんが説明した形そのものである。

**LLM に生のレコードを渡して値段を当てさせるのではない。**

1. まず LightGBM・XGBoost・近傍検索という統計モデルに解かせる
2. その予測値と「実際の価格が分かっている似た車5台」を**証拠**としてまとめる
3. LLM には**最終判断だけ**させる

```python
from unfold import LLMPredictor

model = LLMPredictor(target="車両本体価格_万円", unit="万円",
                     numeric=["車齢", "走行距離_km"], text="装備テキスト")
pred = model.fit(train_df).predict(test_df)
model.explain(0)   # その行がなぜその値になったか
```

### 「正解ラベル」問題は消滅した【PRD §7-1 の決着】

これまで最大の未決事項は「仕様書は 200 件の正解ラベルがある前提だが、
中古車データにその正解は存在しない」というものだった。伊藤さんの説明で解けた。

> トレイン・テスト・バリッドがあると思うので、トレインでやる話かな。中古車価格
> みたいなのはトレーニングデータセットについてはあると。けどテストデータセット
> についてはないので、テストデータの中から一番近いトレインデータを見つけてきて
> 「こんな感じで」予測する。（議事録 00:11:49）

つまり「正解ラベル」とは **通常の train / test 分割の train 側そのもの**であって、
別途つくるものではない。**訓練データの正解価格がそのままフューショットの例になる。**
ラベル作成という工程は存在しない。

あわせて **§7-4（機能B は分類か回帰か）も回帰に決着した。**
伊藤さんの説明は一貫して価格そのものを当てる話で、`predict_proba` 前提の分類設計ではなかった。

### 設計上ゆずらなかった3点

| 決めごと | 理由 |
|---|---|
| **ディスクキャッシュを必ず通す** | 交差検証は同じ行を何度も引くし、実装をいじるたび全行が再課金される。プロンプトのハッシュをキーに保存し、2度目以降は無料。実際、この文書の分析はすべてキャッシュ再生で $0.00 |
| **費用を必ず数える** | 「1行あたりの単価」は実測しないと出せない。呼ぶたびにトークンと金額を積む |
| **証拠は測って決まったレシピを使う** | 類似事例の選び方は §2.2-g の実測に従い、コサイン類似度から車齢・走行距離の標準化距離を引く。意味だけで選ぶと MAE 31.45、混ぜると 18.19 |

`system` プロンプトは全行共通なので Claude 側のプロンプトキャッシュに載せている。
実測で入力 437,559 トークンのうち 312,300 トークンがキャッシュ読み出し（単価 1/10）になった。

## 2. 結果 — **機能B は統計モデルに届かなかった**

各 fold の test から 60 行ずつ、計 300 行で採点した。**統計モデルと LLM を
まったく同じ行で採点している**ので、両者の比較は成り立つ。

| 手法 | MAE（万円） | 備考 |
|---|---|---|
| **LightGBM** | **12.99** | 証拠にした統計モデルの最良 |
| XGBoost | 13.56 | |
| **機能B（LLM の最終判断）** | **13.59** | **★ LightGBM に 0.60 届かず** |
| 近傍5件の価格中央値 | 30.86 | 証拠として渡していた3つ目 |

fold 別では 5 回中 4 回 LightGBM に負けた。

| fold | LightGBM | 機能B |
|---|---|---|
| 1 | 10.55 | 11.53 |
| 2 | 13.14 | 13.85 |
| 3 | 13.20 | 14.02 |
| 4 | 13.85 | **12.83** |
| 5 | 14.18 | 15.72 |

**費用**: 300 行で $3.157（**1行あたり $0.0105**）。全 5,507 行に広げると約 $59。
エラー 0 件、LLM が答えた割合 100%。

PRD §6.2 の受け入れ基準 S6 は「証拠として渡した統計モデル単体の最良値を超えられないなら、
機能B は価値を出していない」だった。**現時点でこの基準は満たしていない。**

## 3. なぜ負けたか — 診断

`scripts/analyze_llm_predictor.py`（LLM を呼ばないので無料）で切り分けた。

### 3.1 LLM の修正は「コイン投げ」になっていた

LLM は 300 行すべてで LightGBM の予測を動かした（平均 7.47 万円）。その内訳:

| | 行数 | 割合 | 幅 |
|---|---|---|---|
| 動いて**良く**なった | 138 | 46.0% | 平均 6.37 万円の改善 |
| 動いて**悪く**なった | 162 | 54.0% | 平均 6.54 万円の悪化 |

**当たり外れがほぼ半々で、幅もほぼ同じ。** つまり LLM の修正は情報を足しておらず、
分散だけを増やしている。「LLM が余計なことをした」というより
「動かすべきかどうかを判断する材料が足りていない」状態である。

### 3.2 犯人は弱い証拠 — 近傍中央値に引きずられていた

証拠として渡した3つのうち、近傍5件の価格中央値は単体で MAE 30.86 と非常に弱い
（LightGBM の 2.4 倍のずれ）。この弱い証拠が LLM を動かしていた。

- LLM の修正方向と、近傍中央値が示す方向の**相関 +0.621**
- **81.0%** の行で、LLM は近傍中央値と同じ向きに動いた

設計書は「複数モデルの出力を集約して渡す」と書いてあるが、**モデルの質を問わずに
並べると、弱いモデルが判断を汚染する**。これは実装したから分かったことである。

### 3.3 confidence は弱いながら信号になっている

LLM に自己申告させた confidence と実際の絶対誤差の相関は **−0.183**
（負なら「自信があるほど当たる」）。弱いが向きは正しい。

| confidence | 行数 | 機能B の MAE | LightGBM の MAE |
|---|---|---|---|
| 0.40〜0.50 | 15 | 23.11 | 16.29 |
| 0.50〜0.65 | 220 | 13.49 | 12.94 |
| 0.65〜0.80 | 61 | **12.21** | 12.34 |
| 0.80〜0.85 | 4 | **4.35** | 13.17 |

**confidence が 0.65 を超えた行では、機能B が LightGBM を上回っている。**
これは信頼度ルーティング（PRD §6.3）が成り立つ可能性を示している。
ただし 0.80 超は 4 行しかなく、この行だけで結論は出せない。

### 3.4 伸びしろ — オラクルとの差が大きい

行ごとに LLM と LightGBM の良いほうを選べたとしたら **MAE 10.06**（実現不可能）。
LightGBM 単体の 12.99 から 2.93 万円も良い。
**「どちらを使うべきか」を見分ける信号さえあれば、伸びしろは大きい。**

### 3.5 単純に混ぜると少し良くなる（ただし有意ではない）

| 混合比 | MAE |
|---|---|
| LightGBM のみ | 12.99 |
| LLM 25% + LightGBM 75% | **12.77** |
| LLM 50% + LightGBM 50% | **12.78** |
| LLM 75% + LightGBM 25% | 13.04 |

これはアンサンブル（複数モデルの平均で分散を減らす定石）が効いた形で、
**LLM の予測に統計モデルとは独立な情報が少しは入っている**ことを示す。

**ただしこの差は統計的に有意ではない。** 行単位のブートストラップ
（データを復元抽出して差の分布を見る手法）で 2,000 回試すと:

- 混合 − LightGBM の MAE 差: **−0.203 万円**
- 95% 区間: **[−0.833, +0.399]**（0 をまたぐ）
- 混合のほうが良い確率: 74.2%
- 5 fold 中 3 fold で混合が勝ち

300 行では判別できない大きさである。**「たぶん少し良い」以上のことは言えない。**

## 4. 追試 — 弱い証拠を外したら勝った（が、僅差）

3.2 の診断が正しければ、近傍中央値を証拠から外せば改善するはずである。
外して測り直した（`--evidence trees`。近傍そのものは類似事例＝証拠2 として渡り続けるので、
フューショットの仕組みは変えていない）。**同じ300行・同じ fold で比較している。**

| 手法 | MAE（万円） |
|---|---|
| 機能B（証拠 = 木2つ + 近傍中央値） | 13.59 |
| **LightGBM** | **12.99** |
| **機能B（証拠 = 木2つのみ）** | **12.85** ★ |
| 機能B（木のみ）50% + LightGBM 50% | **12.65** |

### 4.1 アブレーションの効果は本物

**弱い証拠を外した効果は統計的に有意である。**

- trees − all の MAE 差: **−0.744 万円**
- 95% 区間: **[−1.156, −0.351]**（0 をまたがない）
- trees のほうが良い確率: **100.0%**

同じ行・同じ統計モデルの上で LLM への入力だけを変えた対応比較なので、
差が検出しやすい。**「モデルの質を問わずに証拠を並べると、弱いモデルが判断を汚染する」
という仮説は支持された。**

修正の性質も改善した。平均の動き幅は 7.47 → 5.62 万円に縮み、
動いて良くなった行は 46.0% → 48.0% に上がった。

### 4.2 ただし LightGBM 超えは有意ではない

| 比較 | MAE 差 | 95% 区間 | 勝つ確率 | 勝った fold |
|---|---|---|---|---|
| 機能B（all） − LightGBM | +0.605 | [−0.509, +1.715] | 14.2% | 1/5 |
| **機能B（trees） − LightGBM** | **−0.139** | **[−1.087, +0.706]** | 63.0% | 3/5 |
| **混合（trees 50%）− LightGBM** | **−0.338** | **[−0.820, +0.106]** | 93.0% | — |

**区間が 0 をまたいでいるので、「LightGBM に勝った」とは言えない。**
300 行では ±0.8 万円程度の差は判別できない。混合版が最も惜しい（93%）が、
それでも 95% には届いていない。

### 4.3 confidence によるルーティング（trees 版）

confidence の高い行だけ LLM の答えを採用し、残りは LightGBM に任せる。

| LLM を採用する割合 | MAE |
|---|---|
| 0%（LightGBM のみ） | 12.99 |
| 25% | 12.93 |
| 50% | 12.86 |
| 100% | 12.85 |
| **オラクル（実現不可）** | **10.37** |

**単調に良くなるだけで、途中に山がない。** つまり confidence を使って
「LLM を信じる行」を選んでも、全部信じるのと大差ない。
機能A のフォールバック（`docs/2026-09-01-feature-fallback.md`）では
確信度が明確に効いたのと対照的である。

一方でオラクルとの差は 2.48 万円あり、**「どちらを使うべきか」を見分ける信号は
存在するが、LLM の自己申告 confidence はその信号ではない**、と読める。

## 5. まだ測っていないこと・注意点

- **300 行での測定である。** リーダーボードの全行 12.21（文字TF-IDF 版）とは
  直接比べられない。この文書の中で比べてよいのは、同じ 300 行で測った数字だけ。
- **単一車種（シエンタ）でしか測っていない。** 過去に何度も
  「単一車種では差が出ない」（PRD §2.2-b）現象が起きているので、
  複数車種（Craigslist）でも測り直す必要がある。
- **統計モデルにはテキストを渡していない。** 「テキストを LLM が読めた効果」だけを
  取り出すための設計だが、そのぶん LightGBM 側は本来の実力（全行 12.21）より弱い。

## 6. 結論と次にやること

### 今日わかったこと

1. **機能B は動く。** 実装・疎通・来歴の追跡まで端から端まで通り、エラー率 0%。
   1行 $0.0105、300行で $3.16。
2. **設計書どおりに「複数モデルの出力を全部渡す」のは間違いだった。**
   弱いモデル（近傍中央値・MAE 30.86）を混ぜると LLM がそれに引きずられ、
   MAE が 0.74 万円悪化する（有意）。**証拠は選別して渡す必要がある。**
3. **選別しても、LightGBM を有意には超えられていない**（12.85 対 12.99、勝つ確率 63%）。
   受け入れ基準 S6 は「まだ満たしていない」が正確な表現。
4. **LLM の自己申告 confidence は、機能B ではルーティングの信号にならない。**
   機能A のフォールバックでは明確に効いた（`docs/2026-09-01-feature-fallback.md`）ので、
   課題の型による違いだと考えられる。

### 次にやること（優先順）

1. **行数を増やして決着させる。** 300 行では ±0.8 万円が見えない。
   1,500 行（各 fold 300 行）にすると約 $16。判別できる幅が半分程度になる。
2. **証拠をさらに絞る／足す。** 木2つのうち XGBoost（13.56）も LightGBM より弱い。
   LightGBM 1つだけを証拠にする版、逆にテキスト入り LightGBM（12.21）を足す版。
3. **複数車種（Craigslist）で測り直す。** 単一車種では差が出ない現象（PRD §2.2-b）を
   何度も踏んでいる。**機能B の真価はむしろ複数車種側で出る可能性がある**
   （車種名という定性情報が効くため）。
4. **ルーティングの信号を confidence 以外に求める。** オラクルとの差 2.48 万円が伸びしろ。
   候補は「統計モデル同士の食い違いの大きさ」「近傍の類似度の低さ」「未知語かどうか」。
