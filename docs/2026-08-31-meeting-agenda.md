## A. まず報告する（5分・数字だけ）

8/28〜29 の成果。口頭で言えるように6点に圧縮してある。

1. **評価のやり方を固定した。**
   5-fold 交差検証（データを5等分し、4つで学習・1つで採点、を5回繰り返す）＋
   主指標 MAE（平均絶対誤差。予測が平均で何円ずれるか）。
   全実験が `scripts/eval_protocol.py` を通り `results/*.csv` に自動で残る。
   → 一度決めたら変えない。変えるなら過去の行も引き直す。

2. **機能A（特徴量生成）に値があることを実測で確認した。**
   Craigslist 6万行で、車種名を人手の正規表現で整形すると MAE 2,783 USD、
   埋め込みに任せると **2,620 USD**。**ルールを書かない方が 163 USD 良い。**
   ただしシエンタ（単一車種）では互角（−22.3% vs −21.9%）で、
   **差が出るのは複数車種のときだけ**。
   → 製品デモや評価データは複数メーカーで用意すること、が実測から出た要件。

3. **落とし穴を2つ潰した。**
   - 同じ車が42%重複出稿されており、放置すると R² が 0.880 → 0.914 に水増しされる。
     しかも**非構造テキストを使うほど水増しが大きい**（構造化列だけならほぼ起きない）。
   - Craigslist の `image_url` は **100件中100件が HTTP 404**（→ `docs/2026-08-29-image-urls.md`）。

4. **TabPFN を測った。木系と同着で、超えられなかった。**
   TabPFN は LLM を使わずに表データを解く現在の到達点（Nature 2025）。
   シエンタで同じ列・同じ 5-fold で比べると **TabPFN 12.95 万円 対 LightGBM 12.88 万円**。
   差 0.07 は fold 間の振れ（±0.19〜0.33）より小さく、**統計的に区別がつかない＝実質同着**。
   テキストを足した現在の最良 12.21 には 0.74 届かなかった。
   → **表の列だけを与える限り、器を替えても頭打ちは動かない。伸びしろは非構造テキストの側にある。**
   機能A に賭けるという方針を、実測が支持している（→ `docs/2026-08-29-tabpfn.md`）。

5. **機能B の「似た事例を証拠に渡す」設計に、実測で修正案を出せる状態にした。**
   仕様書の `examples="semantic"`（意味的に似た事例を渡す）をそのまま実装すると、
   渡る事例の質は **MAE 31.45 万円**（統計モデル 12.88 の 2.4 倍ずれる）。
   **距離に車齢・走行距離を混ぜるだけで 18.19 に下がる。**
   §7-2 に挙げた対策3案をすべて実装して比べた結果で、案a と案b は到達点がほぼ同じ（18.2〜18.4）。
   → **実装が単純な案a を既定にする**提案ができる。ただし対策後でも統計モデルには届かないので、
   **証拠の主役は統計モデルの予測値、近傍事例は補助**という順序になる（→ `docs/2026-08-29-denoise.md`）。

6. **機能A の骨組みができた。APIキーが無くても動く形で。**
   設計書の 01〜04（埋め込み → 近傍分類 → 確信度判定）を `unfold/` に実装し、
   05（LLM へのエスカレーション）は差し込み口だけにした。テスト22件。
   シエンタで**正規表現なしにグレード列を作り直す**課題を測ると、
   従来列のみ 17.51 → 機能A で **14.41**（人手の正規表現は 13.60）。
   さらに **confidence が低い行を切り捨てるほど accuracy が単調に上がる**
   （0% で 0.785 → 30% で 0.869 → 50% で 0.904）ことを確認した。
   → **信頼度ルーティングの前提は、LLM を1回も呼ばずに検証できた**
   （→ `docs/2026-08-29-feature-skeleton.md`）。

### B-3. 教師ラベルの起点をどう作るか（PRD §7-1）【実測を持って行ける】

仕様書は「すでに 200 件の正解ラベルがある」前提だが、
**中古車データに「このテキストはどのカテゴリか」という正解は存在しない。**
**今回いちばん重要な設計判断**であることは変わらないが、8/29 に3案を実装して測ったので
手ぶらで議論しなくてよくなった（A-6）。

| 起点 | 中間ラベルの accuracy | 下流の MAE |
|---|---:|---:|
| **値の名前だけを参照事例にする（ラベル0件）** | **0.785** | **14.41** |
| 人手ラベル200件（仕様書の前提） | 0.555 | 16.72 |
| 人手ラベル全件 4,405件 | 0.678 | 16.16 |
| （参考）分類せず埋め込み列のまま | — | 13.97 |

**仕様書が前提にしている「200件の正解」が、3案でいちばん弱かった。**
人手ラベルは参照事例がタイトル全文なので近傍が装備の羅列で決まってしまうのに対し、
値の名前を起点にするとグレードの部分だけを照合する。**件数ではなく参照事例の中身が効く。**

- (a) LLM に最初のラベルを作らせる「起動手順」をライブラリ側に持つ
- (b) 正解は利用者が用意する責任、と割り切る
- **(c) 値の名前を既定の起点にし、人手ラベルは任意にする ← 実測からの推奨**

ただし (c) の優位は「値の名前が本文にそのまま出てくる」データに依存する
（シエンタのタイトルにはグレード名が文字どおり書かれている）。
Craigslist のような自由記述では別途測る必要がある、と併せて伝える。

**決定**:

### B-4. 「CAAFE に負けたら」の方針を先に合意する（PRD §7-6）【TabPFN の分は解決済み】

**TabPFN は測り終えた。**（A-4）シエンタでは木系と同着で、
「LLM を使わない到達点に大差で負ける」という最悪シナリオは起きなかった。
**この論点の半分は消えている。**

残るは **CAAFE**（LLM に前処理コードを書かせる手法。unfold 機能A とは
「LLM がルールを書く」対「ルールを書かずに埋め込みで持つ」で設計が正面から対立する）で、
これは APIキー待ちのため未着手。負ける可能性は現実にあるので、その場合に主張を

- 「精度で勝つ」→「**来歴（どのセルが何由来かを説明できる）・費用対効果で勝つ**」

に組み替えてよいかを**負ける前に**合意しておく。後から言うと言い訳に聞こえる。

なお TabPFN の結果には、負けなかったこと以上の含みがある。
**構造化列だけなら TabPFN でも LightGBM でも同じ壁に当たる**ので、
「モデル選択では超えられない壁を、非構造データの取り込みで超える」という
unfold の立て付けそのものに実測の裏づけがついた。ここは強気に報告してよい。
