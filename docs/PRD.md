## 1. なぜ作るのか

中古車の価格は、表になっている項目（走行距離・年式・修復歴）だけでは決まらない。
実際にはタイトル文や装備の羅列、写真といった**非構造データ**に価格を左右する情報が入っている。
従来の回帰分析ではそれを「ダミー変数」（該当すれば1、しなければ0の列）にするしかなく、
そこが精度の頭打ちの原因だと考えられていた。これが 8/12 ミーティングの出発点である。

`unfold` は、その非構造データを **scikit-learn 互換の API**（`fit` / `transform` / `predict`）で
扱えるようにする Python ライブラリである。中古車価格はその代表ユースケースであり、
ライブラリ自体は汎用に設計する。

### 構想の変遷（どの段階の資料かを見分けるために）

## 2. これまでの進捗（2026-08-29 時点）

### 2.1 できているもの

| 前処理 | 埋め込みに入れる前のノイズ除去を実装・測定（`scripts/text_variants.py`）。**定数語の除去は既定にしてよい**（§2.2-g）。`docs/2026-08-29-denoise.md` |
| 近傍検索 | 意味的類似度だけの近傍は証拠として弱く、距離に数値列を混ぜると MAE 28.92 → 18.19（§2.2-g）。§7-2 の対策案を実測で決着させた |
| 関連研究 | `docs/related-work.md` に14本を3方式に対応させて整理（本 PRD §3 で実測と突き合わせ） |

**評価プロトコルは固定した。**（一度決めたら変えない。変えるなら過去の行も引き直す）

- 分割: KFold(5, shuffle, seed=42) — データを5つに分け、4つで学習し1つで採点することを5回繰り返す
- 主指標: **MAE**（平均絶対誤差。「予測が平均で何円ずれるか」。単位はデータのまま）
- 前処理（TF-IDF・PCA 等）は**必ず fold 内の train だけで fit する**（テストの情報が漏れないように）

### 2.2 測ってわかったこと

#### (a) シエンタ 5,507件 — 従来手法の限界は MAE 22.76 万円

| 構成 | MAE（万円） | 前段からの差 |
|---|---:|---:|
| 中央値（予測しない） | 64.57 | — |
| 線形回帰・従来列（＝スクレイピング当時の分析の再現） | 22.76 | −41.81 |
| LightGBM・従来列（モデルを木に替えただけ） | 17.51 | −5.25 |
| ＋グレード名など構造化列フル | 12.88 | −4.63 |
| ＋装備テキストの文字 TF-IDF（**現在の最良**） | **12.21** | −0.67 |

伸びの中身を1列ずつ分解すると、**グレード名（G / Z / G クエロ…116水準）だけで −3.91 万円**。
これはタイトル文字列から正規表現で抜いた列で、**unfold 機能A が自動化しようとしている作業そのもの**。
一方、装備の羅列を TF-IDF で1300次元足しても −0.67 万円しか動かない
（装備情報の多くがグレード名に織り込み済みで、独立した情報が薄いため）。

#### (b) 埋め込みは人手の正規表現と同等の情報を取り出せた

| 問い | 比較 | 結果 |
|---|---|---|
| 正規表現なしでグレード情報を取れるか | 正規表現版 13.60 vs **タイトル埋め込みのみ 13.68** | ほぼ同等（差 0.08、標準偏差 ±0.42 の範囲内） |
| 埋め込みは TF-IDF に勝つか | 文字TF-IDF 12.21 vs 埋め込み 12.41 | TF-IDF の方がわずかに良い |

**機能A の中核的な前提（人手のルールなしに非構造テキストから特徴量を作れる）は実データで裏付けられた。**
ただし単一車種では正規表現が完璧に効いてしまうので、置き換える動機がない。

#### (c) 複数車種に広げて、初めて機能A の価値が出た【最新】

シエンタの「グレード名」に相当するのが Craigslist の `model` 列（**19,739 種類の自由記述**）。
`f-150 raptor arizona raptor*rust free*icon level kit*...` のように車種・グレード・装備・宣伝文が
混ざっていて、正規表現では芯を抜けない。60,000行サンプルで測った。

| 構成 | MAE（USD） |
|---|---:|
| 中央値（予測しない） | 9,280 |
| 線形回帰・構造化列（車種名を使わない従来手法） | 5,026 |
| LightGBM・構造化列 | 3,234 |
| ＋車種名をそのままカテゴリ扱い | 2,886 |
| ＋車種名を**手書きルール**で正規化（シエンタの正規表現に相当） | 2,783 |
| ＋車種名の文字 TF-IDF | 2,640 |
| ＋車種名の埋め込み（機能A 相当） | 2,620 |
| **＋車種名の埋め込みと文字 TF-IDF の併用（現在の最良）** | **2,596** |
| （参考）手書きルール＋**説明文**（平均2,972文字）の単語 TF-IDF | 2,616 |

**埋め込みが手書きルールに 163 USD 勝った（2,783 → 2,620）。**
シエンタでは起きなかった逆転が、複数車種では起きる。これが「機能A を作る意味」の実測値である。

価格の単位が違う2データセットを比べるため、「構造化列だけの LightGBM から何%縮んだか」で揃える。

| | 人手のルール | 埋め込み |
|---|---:|---:|
| シエンタ（単一車種・116水準） | −22.3% | −21.9% |
| Craigslist（複数車種・9,611水準） | **−13.9%** | **−19.0%** |

**単一車種では互角、複数車種では人手のルールだけが落ちる。**
機能A の価値は **扱う対象の多様性しだい**であり、1車種のデモでは価値が見えない。
**製品デモや評価データは複数メーカーで用意すること**が要件になる。

ただし差の大きさは正直に見る必要がある。埋め込み 2,620（±8）と文字 TF-IDF 2,640（±16）の
差は 19 USD で、5 fold 中4つで勝った程度。**埋め込みは文字 TF-IDF に対して「同等〜わずかに上」であって
圧勝ではない。**手書きルール（2,783）に対する 163 USD の差ははっきりしている。

なお最下段の E（2,616）は上の積み上げの続きではなく、**手書きルールに説明文3,000文字を足した別系統**。
これが車種名を文字 TF-IDF で扱っただけの 2,640 とほぼ同じという事実自体が、
**長い自由記述は短い車種名の焼き直しが大半**であることを示している。

#### (d) ただし埋め込みは万能ではない — 2つの反証

**反証1: 未知の車種名では文字 TF-IDF の方が強い。**
テスト行の **10.7%（6,424行）** は、訓練データに1度も出てこない車種名だった。そこだけ切り出すと：

| 手法 | 既知の車種名 MAE | 未知の車種名 MAE |
|---|---:|---:|
| 手書きルール | 2,623 | 4,118 |
| 文字 TF-IDF | 2,511 | **3,715** |
| 埋め込み | **2,470** | 3,873 |
| 埋め込み＋文字 TF-IDF の併用 | 2,455 | 3,768 |

未知語こそ埋め込みの独壇場だと想定していたが、実際は文字 TF-IDF が **158 USD** 良い。
文字 TF-IDF は2〜4文字の並びを見るので、`f-250 lariat` を知らなくても
`f-2` `250` `lar` という既知の断片に分解できる。一方 e5-small は文全体を1つのベクトルにするため、
固有名詞そのものを知らないと分解しきれない。

**そこで両方を入れると、全体で最良の 2,596 になった（埋め込み単体 2,620 から −25）。**
既知の車種名では埋め込みが、未知の車種名では文字 TF-IDF が効くという役割分担があり、
2つの表現は競合ではなく補完の関係にある。ただし未知語だけを見ると併用（3,768）は
文字 TF-IDF 単体（3,715）にまだ届いていない。

**反証2: 埋め込みの近傍検索は「価格の近さ」を拾わない（機能B への直接の指摘）。**
シエンタのタイトル埋め込みで類似度 0.96 以上の3台を引くと、価格が 156 / 265 / 176 万円とばらばらになった。
店舗名の書式が同じことに反応していたためである。グレード別に 400 組ずつサンプリングして
平均類似度を測ると、**同一グレード同士 0.915〜0.928 に対し、異なるグレード同士 0.909〜0.915** と差がない。

- 教師あり学習（LightGBM に384次元を渡す）… 価格と関係のある次元を選べる → **効く**
- 近傍検索（384次元を1つの距離にまとめる）… 埋もれた情報は取り出せない → **効かない**

仕様書の機能B は `examples="semantic"` で「似た事例」を証拠として LLM に渡す設計だが、
**この「似ている」は価格の近さを意味しない。** 機能A の 03「近い正解例を探す」も同じ構造である。

#### (e) 重複排除をサボると、非構造テキストを使うほど精度が水増しされる【要件に直結】

Craigslist データは同じ車が複数地域に出稿されており、**同一の車台番号（VIN）が最大 261 件**、
価格まで同一だった。フィルタ後 346,371 行のうち **42% が重複**で、排除して 200,374 行になる。
残したまま普通に交差検証すると、**まったく同じ車が訓練側と答え合わせ側の両方に入る**。

| | MAE | R² |
|---|---:|---:|
| 重複を残した場合（誤り） | 2,529 | 0.914 |
| 重複排除した場合（正しい） | 2,640 | 0.880 |

**注目すべきは、この水増しが構造化列だけのモデルではほとんど起きないこと**（3,270 vs 3,234）。
年式・走行距離だけでは個体を特定できないが、車種名のテキストが入ると「その1台」を思い出せてしまう。
つまり **非構造テキストを特徴量に使うほど、重複排除の手抜きが効いてくる**。

これは unfold にとって他人事ではない。`fit` / `predict` の形で提供すれば、
利用者は素の交差検証を回す。**ライブラリが非構造テキストを特徴量にする道具である以上、
重複検知は利用者の心得ではなく製品側の責務になりうる**（→ §7-5）。

#### (f) TabPFN は LightGBM に並んだが、超えなかった【最新・P0.5 の片方】

「LLM を使わない側の到達点」を置くために TabPFN を測った（R6 / S5）。
TabPFN は人工の表データで事前学習済みの Transformer で、**その場での訓練をしない**。
訓練データを入力として丸ごと渡し、1回の推論で答えを出す（in-context learning）。
Transformer を使うが **LLM ではない**（学習したのは言葉ではなく表データの構造）。

シエンタ 5,507行・同じ列・同じ 5-fold で比較した。

| 手法 | MAE（万円） | 振れ幅 | 5-fold の所要 |
|---|---:|---:|---:|
| C2 ＋装備テキストの文字TF-IDF（全体最良） | **12.21** | ±0.42 | 数秒 |
| B LightGBM・構造化列フル（**同じ列＝直接の相手**） | **12.88** | ±0.19 | 数秒 |
| **F TabPFN・構造化列フル（n_est=8）** | **12.95** | ±0.33 | **1,015秒** |
| F TabPFN・構造化列フル（n_est=1） | 13.06 | ±0.32 | 148秒 |

**同じ列なら 12.88 対 12.95。差 0.07 は fold 間の振れ（±0.19〜0.33）より小さく、
統計的に区別がつかない＝実質同着。** 一方、テキストを足した C2（12.21）には
0.74 差をつけられており、こちらは振れ幅を超える実質的な差である。

**含意: 表の列だけを与える限り、器を替えても頭打ちは動かない。伸びしろは非構造テキストの側にある。**
これは機能A（特徴量生成）に賭けるという本プロジェクトの前提を支持する。
ただし「TabPFN に楽勝した」わけではない。同着なので、LightGBM を使う理由は
精度ではなく速度（200〜400倍）の側にある。

#### (g) 埋め込み前のノイズ除去と、近傍の作り直し【最新・§7-2 と §7-3 に決着】

(d) 反証2（埋め込みの「似ている」が価格の近さを意味しない）への対策を実装して測った。
詳細は `docs/2026-08-29-denoise.md`。**入力テキストを削る前処理は車種に依存しない汎用ルールだけ**を使った
（車種固有の知識を書いた時点で機能A の趣旨が崩れるため）。

**1. 削るとグレードは分離できるようになる。** 同一グレードのペアと異グレードのペアを
順位で見分ける AUC は 0.637（生）→ 0.781（先頭区切り＋定数語除去）。
モデルを替えず学習もせず、**入力から情報のない語を抜いただけ**である。

**2. しかし分離の改善は価格予測の改善と一致しない【重要】。**
近傍5件の価格中央値を予測値にして 5-fold で測ると、分離が最良の版（AUC 0.781）は 31.86 万円、
分離が中位の「定数語の除去」（AUC 0.707）が 28.92 万円で**順位が入れ替わる**。
グレードを当てる削り方と価格を当てる削り方は別物で、
**中間ラベルの精度を上げにいくと下流の精度を落としうる**（→ §7-3 の論点に直接の実測）。

**3. 近傍の選び方は、埋め込みの作り方より効く。**

| 近傍の選び方 | MAE（万円） |
|---|---:|
| 意味的近傍のみ（生） | 31.45 |
| 意味的近傍のみ（定数語除去） | 28.92 |
| 数値距離のみ（埋め込みを使わない） | 24.45 |
| **距離に車齢・走行距離を混ぜる（§7-2 案a・定数語除去）** | **18.19** |
| 粗い予測の価格帯±20%に絞ってから意味的に選ぶ（§7-2 案b） | 18.32 |
| （参考）LightGBM・構造化列フル | 12.88 |

**§7-2 の案a と案b は到達点がほぼ同じ（18.2〜18.4）**なので、実装が単純な案a を既定にしてよい。
埋め込み自体も寄与している（数値距離のみ 24.45 → 併用 18.19）ので、
「意味的な近さは無価値」ではなく「単独では使えない」が正しい。
ただし対策後でも統計モデル（12.21）には 6 万円届かない。
**機能B に渡す証拠の主役は統計モデルの予測値で、近傍事例は補助**という順序づけになる。

**4. 副作用。** 定数語の除去は教師あり学習（D2 相当）も 13.68 → 13.29 と改善し、
埋め込みの計算時間も短くなる。一方「先頭区切りまで」は 13.79 と悪化するので採らない。

なお**この前処理は Craigslist には効かない。** `model` 列は平均 9.9 文字ですでに短く、
区切り記号を含む行が 0.7%、メーカー名を含む行が 0.6% しかない。
**ノイズ除去が効くかは列の書式しだい**で、「モデル名＋装備の羅列」が1列に詰まった形式でこそ効く。

#### (h) 機能A の骨組みを実装し、教師ラベルの起点3案を測った【最新・§7-1 に材料】

`unfold/` に機能A を実装し、**シエンタでグレード列を正規表現なしに作り直す**課題で
起点の作り方を比べた。詳細は `docs/2026-08-29-feature-skeleton.md`。

| 起点 | 中間ラベルの accuracy | 下流の MAE（万円） |
|---|---:|---:|
| A2 従来列のみ（下限） | — | 17.51 |
| **(b) ラベル0件・値の名前だけを参照事例にする** | **0.785** | **14.41** |
| (a) 人手ラベル200件（仕様書の前提） | 0.555 | 16.72 |
| (a') 人手ラベル全件 4,405件 | 0.678 | 16.16 |
| **(c) 埋め込み列（分類を経由しない）** | — | **13.97** |
| Ab1 正規表現のグレード名（上限） | 1.000 | 13.60 |

**1. 仕様書が前提にしている「人手ラベル200件」が3案でいちばん弱かった。**
ラベルを1件も使わない (b) が下流 MAE で 2.31 万円良い。人手ラベルは参照事例が
**タイトル全文**なので近傍が装備の羅列で決まるのに対し、値の名前を参照事例にすると
グレードの部分だけを照合するため。**件数ではなく参照事例の中身が効いている。**
ただしこの優位は「値の名前が本文にそのまま出てくる」データに依存する（§7-1 の判断材料）。

**2. 分類を経由しない (c) が最良。** カテゴリに丸める時点で情報が落ちる
（宣言10値でカバーできるのは 88.1%）。**機能A の出力を型のついた列に限定すべきか**という
設計上の問いがここに出る。§7-3 と同じ構造の話である。

**3. 信頼度ルーティングの前提は成り立つ。** confidence の低い順に切り捨てると
accuracy が単調に上がった（0% 0.785 → 10% 0.819 → 30% 0.869 → 50% 0.904）。
**LLM を1回も呼ばずに確認できた**ので、P4 の半分は APIキー待ちのまま進められる。
一方 confidence の絶対値はまだ較正されていないので、閾値ではなく
`escalate_rate`（低い順に何割を回すか）で指定する API を足した。

#### (i) 機能A を複数車種で測った【最新・P1 完了】

シエンタで出た結果が一般化するかを Craigslist 60,000行（同じ 5-fold・同じ列）で確かめた。
詳細は `docs/2026-08-29-feature-vehicles.md`。既測の A2（3,234）と B2（2,783）が
そのまま再現されており、条件は揃っている。

| 手法 | MAE（USD） |
|---|---:|
| A2' 構造化列のみ | 3,233.54 |
| B2' 手書きルール正規化 | 2,782.95 |
| F(a)' 機能A・人手ラベル200件 | 2,781.36 |
| F(b)' 機能A・ラベル0件（値の名前だけ） | 2,789.35 |
| **F(c)' 機能A・埋め込み列（既定エンコーダ）** | **2,601.14** |
| F(c-e5)' 機能A・埋め込み列（e5 を API 経由） | 2,613.86 |
| （参考）D4 埋め込み＋文字TF-IDF の併用（従来の最良・手組み） | 2,596 |

**1. 機能A の埋め込み列が従来の最良に並んだ。** 2,601 は文字TF-IDF（2,640）と
e5 埋め込み（2,620）を単体で上回り、手で組んだ併用（2,596）と実質同着。
**特徴量を手で組まず1行の API 呼び出しで到達している**ことに意味がある。

**2. §2.2-h の「値の名前 > 人手ラベル」は一般化しなかった。**
Craigslist では 2,781／2,789／2,783 と3つとも同着。原因は宣言値の被覆率で、
シエンタは10値で 88.1% を覆えたのに対し、Craigslist は60値で **34.5%** しか覆えない
（真の水準数 5,156）。**カテゴリに丸める設計は高カーディナリティの自由記述で破綻する。**
→ `type="embedding"` を機能A の既定に据えるべき、というのが2データセット共通の結論。

**3. 信頼度ルーティングは複数車種でも単調**（0% 0.345 → 30% 0.415 → 50% 0.521）。

#### (j) 未知の車種名で測り直した【最新・P2 完了】

テスト行の 10.7%（6,424行）は訓練データに無い車種名を持つ。既測ではここで
**文字TF-IDF が未知語に強く（3,715）、e5 埋め込みが既知語に強い（2,470）**という
役割分担が出ていた。機能A の既定エンコーダ（文字 n-gram TF-IDF を SVD で 256 次元に圧縮）が
どちら側に着地するかを測った。詳細は `docs/2026-08-29-feature-unseen.md`。

| 手法 | 全体 | 既知 | 未知 |
|---|---:|---:|---:|
| B2 手書きルール | 2,783 | 2,623 | 4,118 |
| C2 文字TF-IDF | 2,640 | 2,511 | 3,715 |
| D1 e5 埋め込み | 2,620 | 2,470 | 3,873 |
| D4 e5＋文字TF-IDF（従来の最良） | 2,596 | 2,455 | 3,768 |
| **F(c)' 機能A・既定エンコーダ** | 2,599 | **2,464** | **3,730** |
| F(c-e5)' 機能A・e5 を API 経由 | 2,621 | 2,470 | 3,886 |
| **F(d)' 機能A＋文字TF-IDF** | **2,588** | 2,455 | **3,700** |

**1. 既定エンコーダは未知語に強い側に着地した**（3,730。e5 より 143 良い）。
SVD で圧縮しても文字断片の情報は失われていない。

**2. しかも既知語でも強く、単一の表現で両取りになっている**（既知 2,464 は
文字TF-IDF 単体より 47 良く、e5 と同等）。**これまで併用でしか得られなかった性質**で、
密ベクトルにしたことで「似た綴りの車種が近い」構造を木が軸として使えるためと考えられる。
→ **torch なしという実務上の理由で選んだ既定が、精度でも正当化された。**

**3. 未知語は依然として弱点。** 最良でも未知 3,700 対 既知 2,455 で 1.5 倍ずれる。
機能B が効きうる場所であり、**LLM に回す行の選び方として confidence だけでなく
「訓練データに無い値かどうか」も使える**（価格を見ないので実装は容易）。

### 2.3 未着手・ブロッカー

- **LLM を呼ぶ部分は全部未着手。** `.env`（APIキー）が未作成のため機能B と機能A のフォールバックが動かせない

  「Craigslist の `image_url`（9割充足）を使えば検証可能」と書いていたが、**これは誤りだった。**
  100件を実際に取得したところ **100件すべて HTTP 404**。投稿ページ本体も同様に削除済みを返す。

  新旧が混在していないので全体が失効していると判断できる（craigslist は掲載期間経過後に

- **勝ち筋の見立ては先行事例と一致している。** 「LLM は特徴量生成器・埋め込み器、予測器は木系」という

- **新規性は比較の相手にある。** 先行事例は「木系 vs LLM」を比べているが、
  **「人手で書いた前処理ルール vs 埋め込み」を同一データ・同一プロトコルで比べていない**。
  §2.2 (b)(c) はまさにそれを測った結果であり（単一車種では同等、複数車種では埋め込みが 163 USD 勝つ）、

  構造化列に集中しているため、「テキストを読ませて価格を当てる」筋は弱い。
  機能B は証拠を集約する層としてのみ意味を持つ。

## 5. 対象ユーザーとユースケース

| ユーザー | やりたいこと |
|---|---|
| データ分析担当（社内） | 自由記述の混じった手持ちデータを、前処理コードを書かずにモデルに載せたい |
| 中古車の価格査定 | タイトル・装備・写真から相場を出し、なぜその値かを説明したい（代表ユースケース） |
| 汎用（churn 予測など） | 仕様書に例がある。中古車に限定しない |

```python
df["vehicle_type"] = Feature(
    source="image", type="category", values=["sedan", "suv", "truck", "van"],
).fit_transform(df)
```

### 5.1 スコープ

**やること**

- 機能A: `Feature` — 非構造列を型付き列に変換する
- 機能B: `LLMPredictor` — 統計モデルの予測と類似事例を証拠として LLM に渡し、最終判断させる
- 信頼度ルーティング（adaptive）: 確信度が閾値を下回った行だけ LLM に回す
- 来歴（provenance）: 各セルの由来・確信度・参照事例・費用の保持と `explain()`
- キャッシュ: 同じ行に二度課金しない
- 上記を測るための評価基盤（**実装済み**）

**やらないこと**

- 方式②（LLM によるモデル選択の自動化）— R8 のとおり先行研究はあるが、仕様書の段階で外れている
- スクレイピング機能そのもの（データはすでに手元にある）
- エンドユーザー向け UI・推薦ランキング（エントリーシート段階の構想であり、現在地ではない）
- 分散処理・大規模スケール（当面は数万行が対象）

## 6. 機能要件

### 6.1 機能A — `Feature`（特徴量生成）

**目的**: 画像・自由記述などの非構造列を、宣言だけで型付き列にする。

| # | 段階 | 要件 |
|---|---|---|
| 01 | 教師ラベル | 既存の正解ラベルを参照点にする。**ゼロから始める手順が別途必要（§7-1）** |
| 02 | 埋め込み | 1レコード1ベクトル。**キャッシュ必須**（1行の埋め込みは一度だけ計算する） |
| 03 | 近傍探索 | 類似度＋ラベル一致度から確信度を出す。**距離の定義に要検討事項あり（§7-2）** |
| 04 | 確信できれば | ラベルを返す。LLM 呼び出しなし |
| 05 | 確信できなければ | LLM にエスカレーションし、答えを新しいラベル候補として書き戻す |

出力型: `binary` / `category` / `int` / `float` / `ordinal` / `multilabel` / `embedding`
入力: 単一列（`source="description"`）または複数列（`source=["image", "description"]`）

**LLM に期待する仕事を絞り込む。** 実測では「埋め込み → 近傍で分類」だけの構成が
文字 TF-IDF から得る上積みは **20〜45 USD** しかない。この程度なら埋め込みを回す価値は薄い。
差が出るとすれば **表記体系そのものの正規化**（`f-150 raptor` / `f150 raptor` / `f 150 raptor` を
同じ型に落とす）であり、**そこが機能A における LLM の担当範囲**である。
埋め込みは近傍探索の土台、LLM は表記の統合、と役割を分けて実装すること。

**表現は1つに固定しない。** §2.2(d) のとおり埋め込みと文字 TF-IDF は得意な場面が違うので、
**併用を既定の選択肢として持つ**こと（実測で全体最良の 2,596）。

**受け入れ基準**: S1〜S5。
**測り方の原則**: 中間ラベルの accuracy ではなく、**下流の価格 MAE で測る**。
中間ラベルが正確でも価格が当たるとは限らないうえ、下流指標なら正解ラベルが要らない（§7-3）。

### 6.2 機能B — `LLMPredictor`

**目的**: LLM に生レコードを渡して当てさせるのではなく、
XGBoost・LightGBM・semantic k-NN に先に解かせ、その予測値と類似事例を「証拠」として渡し、
最終判断だけさせる。R1（LLM は補完として有効）と R4（少数サンプル域でしか直接予測は competing しない）が、
この構造を支持している。

```python
model = LLMPredictor(target="resale_band", models=[xgb, lgbm, semantic_knn],
                     examples="semantic", n_examples=5)
```

要件:

- 複数の統計モデルの出力を集約して LLM に渡すこと
- 少数事例（few-shot）は**行ごとに検索して差し替える**こと（一度貼って使い回さない）
- **類似事例の選び方は再設計が必要**（§2.2-d 反証2 / R3）。埋め込み類似度のみで選ぶと無関係な事例を根拠に渡す
- 中古車価格は連続値なので、`predict_proba` 前提の分類設計をどう当てるかの決着が必要（§7-4）

**受け入れ基準**: S6。証拠として渡す統計モデル単体の最良値を超えられないなら、機能B は価値を出していない。

### 6.3 信頼度ルーティング（`AdaptivePredictor`）

閾値ひとつで「全行を LLM に投げる」と「1行も投げない」の間を連続的に動かせること。
閾値を動かしたときに **精度・レイテンシ・費用の3つが同時に見える**こと。
LLM が答えた行は教師ラベル候補としてキューされ、承認すると次回は高速パスが広がる（能動学習）。

これは 8/12 ミーティングで課題に挙がった「キャッシュ活用による LLM 予測の軽量化」への回答にあたる。

**ルーティングの基準は confidence だけではない。** 実運用では新車種・新グレードが絶えず入ってくる
（今回のデータで訓練データに無い車種名が 10.7%）。埋め込みだけの構成はこの層で弱いので、
**「未知語かどうか」でエスカレーションする変種**を用意する価値がある。

**ルーティングは精度対策であると同時に計算量対策でもある。** 説明文（平均2,972文字）の埋め込みは
6万件を CPU で回すと数時間かかるため今回見送った。**どの行を重い処理に回すかを絞る仕組みが先にないと、
長い自由記述はそもそも扱えない。**

### 6.4 来歴（provenance）と検査 API

| API | 返すもの |
|---|---|
| `model.explain(X)` | そのセルの由来（human / model / llm）・確信度・参照した事例・費用 |
| `model.confidence(X)` | 行ごとの確信度（実行を確定する前に見られること） |
| `model.examples(X)` | 推論に使った事例 |
| `model.cost(X)` | 実行前の費用見積もり |

特徴量はそれを作ったラベルとセットでバージョン管理し、
3ヶ月後の再実行で同じ数字が出るか、どのラベルが変わったかが分かること。

### 6.5 非機能要件

| 項目 | 要件 |
|---|---|
| API | scikit-learn 互換（`fit` / `transform` / `fit_transform` / `predict` / `predict_proba`） |
| 差し替え | 埋め込みモデル・LLM・統計モデル・ストレージは設定で差し替えられること |
| 再現性 | seed 固定・fold 内 fit の原則をライブラリ側で守らせること |
| **リーク防止** | 重複レコードの検知。非構造テキストを特徴量にすると重複が精度を水増しするため（§2.2-e）、少なくとも警告を出せること |
| 費用 | 同じ行に二度課金しない。実行前に見積もりを出せる |
| 環境 | Python ≥ 3.10。埋め込み計算は依存衝突を避けるため隔離環境に分けてよい |
| **GPU 非前提** | 開発機（Intel Mac / Radeon Pro 560X）では **GPU を使っても速くならない**ことを実測（埋め込みで CPU 4.1ms/件 対 MPS 24.6ms/件）。torch も 2.2.2 が上限で、GPU 前提の新しい依存は入らない。**CPU で完結する構成を既定にする** |
| データ規模 | 数万行を CPU のみで扱えること（現状: 5,513件×2列の埋め込みに約16分。TabPFN はシエンタ 5,507行の 5-fold に17分） |

## 7. 未決事項（次回ミーティングの論点）

1. **教師ラベルの起点をどう作るか【実測が出た・§2.2-h】。** 仕様書は「すでに 200 件の正解がある」前提だが、
   中古車データに「テキスト→カテゴリ」の正解は存在しない。実装して測ったところ、
   **(b) 値の名前だけを参照事例にする案が、人手ラベル200件より下流 MAE で 2.31 万円良かった**
   （14.41 対 16.72）。ラベルを作らせる前に「値の名前で足りないか」を確かめる価値がある。
   残る判断は (i) LLM にシードを作らせる起動手順をライブラリに持つか、
   (ii) (b) を既定にして人手ラベルは任意にするか、(iii) 利用者の責任にするか。
   **推奨は (ii)。**ただし複数車種で測り直すと3案とも同着になり（§2.2-i）、
   **(b) の優位はシエンタ固有だった**。より重要なのは
   **「そもそもカテゴリに丸めず `type='embedding'` を既定にする」**という判断で、
   これは2データセットとも支持している（丸めた版より下流 MAE が良い）。
2. **類似事例の選び方【対策を3案とも実測済み・§2.2-g】。** 埋め込みのコサイン類似度だけでは
   価格の近さを拾わない（MAE 31.45）。(a) 数値列を含めた距離にすると **18.19**、
   (b) 価格帯で絞ってから意味的に並べると 18.32 で**到達点はほぼ同じ**、
   (c) 入力のノイズ除去は単独では 28.92 止まり。**推奨は (a)（実装が最も単純で同着）+ (c) の併用。**
   残る判断は「近傍事例を証拠としてどこまで信用するか」で、
   対策後でも統計モデル（12.21）には届かないため、**証拠の主役は統計モデルの予測値**になる。
3. **機能A の評価指標を中間ラベルの accuracy にするか、下流の MAE にするか【実測が出た】。**
   本プロジェクトの立場は下流 MAE（正解ラベル不要という利点がある）。
   §2.2-g で**両者の順位が実際に入れ替わった**（グレード分離 AUC 最良の版が、価格 MAE では負ける）。
   中間ラベルの精度を評価軸にすると、下流を悪くする前処理を採用しうる。
   §2.2-i はさらに強い例で、**中間ラベルを作らない構成（`type="embedding"`）が
   下流では最良**だった。中間ラベルの accuracy は定義すらできないので、
   その指標では最良の構成を評価できない。
4. **機能B を分類にするか回帰にするか。** 仕様書は `predict_proba` 前提だが、中古車価格は連続値。
5. **重複排除をライブラリの責務にするか、利用者の心得にするか。**
   今回のデータでは重複を残すだけで R² が 0.880 → 0.914 に水増しされ、
   しかも**非構造テキストを使うほど水増しが大きくなる**（§2.2-e）。
   unfold はまさに非構造テキストを特徴量にする道具なので、検知・警告を製品側に持つ選択肢がある。
6. **CAAFE を機能A の比較対象に加えるか（R2）。** 実装が公開されており、
   「LLM がルールを書く」対「ルールを書かずに埋め込みで持つ」を同一データで比べられる。
   ここで勝てれば機能A の設計判断そのものが正当化される。
7. **点推定だけで評価するか、分布も出すか（R5・R7）。** 中古車価格を扱った ProbSAINT は
   「点推定はブースティング同等、価値は不確実性の側」と述べている。指標に予測区間を入れるかどうか。
8. **画像モダリティ（P5）をどうするか。** Craigslist の画像は全滅しており、
   手持ちのデータでは検証できない（§2.3）。選択肢は (a) P5 を落として機能A・機能B に集中する、
   (b) 画像つきの別データを探す、(c) カーセンサーで画像を再取得する。
   **推奨は (a)。** (b) は探索コストが読めず、(c) は単一車種なので
   「単一車種では差が出ない」問題（§2.2-b）を踏み直すことになる。
   仕様書の `Feature(source="image", ...)` は API として設計だけ残す案。
9. **APIキーの入手経路。** ブロッカーとして最優先。**残る未測定項目（S4・S6・S7）はすべてこれ待ち。**

**S1・S2 の線は行数とセットで固定する。** 今回の測定は 20万行から 6万行に間引いたもので、
全20万行にすると未知語率が 10.7% → 6.4% に下がり、未知語の指標（S2）の意味が変わる。
比較するときは必ず同じ行数・同じ seed で引き直すこと。

P0.5 を P1 より先に置く理由は、**LLM を使わない到達点（TabPFN）と LLM の別の使い方（CAAFE）を
知らないまま機能A を作ると、改善したかどうかを判定できない**ため。R6 の指摘そのものである。
**TabPFN 側は片付いた**ので、残る P0.5 は CAAFE のみ（APIキー待ち）。
なお TabPFN は「構造化列だけなら木と同着」だったので、**埋め込み384次元を足した TabPFN**
（非構造テキストをどちらの器がうまく使えるか）は別の問いとして残っている。
P1 の前提だった「埋め込みの入力からノイズを除く前処理」は**実施済み**（§2.2-g）。
定数語の除去を既定にし、近傍検索は距離に数値列を混ぜる形にする。
