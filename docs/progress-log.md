# 進捗ログ — プロジェクト開始からの流れ

**目的**: 「いつ・何をして・何がわかったか」を時系列で1枚にまとめる。
詳細は各日の `docs/2026-*.md` にあるので、ここは索引と流れの把握に使う。
**運用**: 作業が一段落するたびに、その日の欄に箇条書きを足していく。

## 2026-08-28（初日）— 土台づくり

- 議事録・サンプルデータ・`CLAUDE.md` を置き、プロジェクトの前提を文書化した
- **データの置き場所を「再現できるか」で4分類**に整理した
  （`raw/` 再取得可・`scraped/` 再取得不可・`processed/` 再生成可・`sample/` 抜粋）。
  再現できるものは git に入れず、手順のほうを git に入れる方針
- Python 3.12 + venv の分析環境を構築した（システムの 3.9 は使わない）
- 探索用ノートブックを追加し、セットアップを1セルに統合した
- カーセンサーからスクレイピングしたシエンタのデータを追加し、クレンジングを書いた
- 先行研究のメモを追加した
- **巨大ファイルの `git add` を機械的に拒否するフック**を作った
  （100MB 以上は拒否・25MB 以上は確認）。git は一度入れた巨大ファイルを永久に残すため

## 2026-08-29 — 測る土台と、機能A の骨組み

- **評価プロトコルを固定した**（`scripts/eval_protocol.py`）。
  5-fold 交差検証・主指標 MAE・前処理は fold 内の train だけで fit。
  全実験がここを通り `results/*.csv` に自動追記される
- **シエンタ（単一車種・5,507行）でベースラインを測った**。
  従来の線形回帰 22.76 万円 → LightGBM 17.51 → 構造化列フル 12.88 → 文字TF-IDF 12.21
- 埋め込み（`multilingual-e5-small`）を計算し、**人手の正規表現と同等の情報を
  テキストから取り出せる**ことを確認した（13.60 対 13.68）
- **Craigslist（複数車種・20万行）でも測った。**ここで重要な発見が2つ:
  - **同一車の重複出稿が42%**あり、放置するとランダム分割で train と test に
    同じ車が入る（MAE が 4.2% 良く見える）。1台1行に潰す処理を入れた
  - **複数車種では埋め込みが手書きルールに勝った**（2,620 対 2,783）。
    シエンタでは起きなかった逆転。**機能A の存在価値の実測値**
- PRD（要件定義）を追加し、8/12 ミーティング・伊藤さんの仕様書・実測を突き合わせた
- **画像URLの生存確認を先に15分でやったら、100件中100件が 404 だった。**
  P5（画像モダリティ）は実施不能と判定。半日〜1日の無駄を回避
- TabPFN を測定（12.95）。LightGBM と実質同着で、脅威ではないと確認
- 埋め込み前のノイズ除去と近傍検索を作り直した。
  **意味的類似度だけの近傍は証拠として弱く**（MAE 28.92）、
  距離に数値列を混ぜると 18.19 まで改善
- **機能A（`Feature`）の骨組みを実装**（設計書の 01〜04。05 は差し込み口のみ）。
  教師ラベルの起点3案を実測し、**「ラベル0件・値の名前だけ」が
  人手ラベル200件より 2.31 万円良い**という、仕様書の前提を覆す結果を得た
- 機能A を複数車種で測って P1 完了（2,601。手組みの最良 2,596 と実質同着）
- **未知の車種名だけで測り直して P2 完了。**機能A の既定エンコーダ
  （文字 n-gram TF-IDF + SVD256）が、未知 3,730・既知 2,464 で
  **1つの表現で両取り**になっていることを確認

## 2026-09-01 — 機能B と、リークとの戦い

- **機能B（`LLMPredictor`）を実装**し、シエンタで初回実測（P3）。
  統計モデルを有意には超えられず**不合格**（12.85 対 12.99）
- 実装で譲らなかった3点: ディスクキャッシュ必須・費用を必ず数える・
  証拠のレシピは実測で決まったものを使う
- ルーティング信号を6通り探索し、機能B の測定を2データセット対応にした
- 検査 API の取り違えを検知する仕組みと、キャッシュ破損への耐性を入れた
- **Craigslist（複数車種）で測り直したら合格した**（2,335 対 比較線 2,591、
  −9.9%、p=0.009、5/5 fold で勝ち）。受け入れ基準 S6 を満たした
  - 差の理由は **LLM の修正が当たる率**（シエンタ 46% = コイン投げ、
    Craigslist 67%）。テキストに情報がない場所では LLM も効かない
- **前日に立てかけた一般則を撤回した。**「弱い証拠は LLM を汚染する」は
  複数車種では再現せず符号も逆で、**シエンタ固有の現象**だった
- **自由記述を渡したら40%改善して、疑ったらリークだった。**
  採点した600行のうち262行（43.7%）の説明文に価格そのものが書かれていた。
  価格記載のある行だけ65%改善という偏りが動かぬ証拠
  - 対策を**ライブラリ側の責務**にした（`mask_amounts()` で既定で伏せる）。
    出品・求人・不動産など自由記述に答えが書かれるデータでは常に起きるため
  - 伏せて測り直しても **23.6% の改善**が残り、効果は本物だと確認できた
- 事前スクリーニング（`unfold.screen()`）とレイテンシ計測を追加した。
  副産物として「**スクリーニングと LLM の実測が食い違ったらリークの兆候**」
  という検査手順を得た
- 機能A の LLM フォールバック（設計書05）を実測（P3.5）。
  **確信度の低い15%を回すと正解率 0.873 → 0.942 で、回した行は全問正解。**
  「迷った行だけ LLM」という設計の前提が裏付けられた
- 精度・費用・レイテンシの曲線を取得（P4）。最良の信号は
  「LightGBM と XGBoost の食い違い」＝統計モデル自身が迷っている行
- ノートブックに後半（複数車種・リーク・スクリーニング・レイテンシ）を追記
- **信頼度ルーティングを `AdaptivePredictor` としてライブラリ化**（P4.5）。
  これで設計書の3本柱がすべて API になった。
  6万行に機能Bを素で当てると $516・17時間かかるため、絞る仕組みは必須だった

## いま残っている宿題

- **CAAFE との比較（P0.5 の残り）** — 「LLM にコードを書かせる」対
  「コードを書かせず埋め込みで持つ」。機能A の設計判断そのものを問う唯一の未完項目
- **重複検知のライブラリ化** — 自由記述の伏字は製品側に入れたが、
  重複排除は「利用者の心得」のまま。同種の事故なので揃えるべき
- **画像モダリティの扱い** — 実施不能。API の設計だけ残す案が推奨
- **予測区間を出すか** — 点推定だけでなく幅で答えるか
- **来歴 API の整備** — 各セルの由来・確信度・費用を辿れるようにする（仕様書の必須要件）

## 通して言えること

- **効く条件つきで示せた。** テキストに本当に情報がある場所（複数車種）では
  既存の最良手法を上回り、飾りでしかない場所（単一車種）では上回らない
- **良すぎる結果は必ず疑う。** リークを2件（重複出稿・説明文の価格）見つけ、
  どちらも「部分集合に分けて採点する」ことで検出した
- **間違った一般化は撤回する。** アブレーションの結論を1件、実測に基づいて訂正した
- **着手前に前提を15分で確認する。** 画像URLの生存確認がこれにあたり、
  最大の作業項目を1つ、無駄になる前に落とせた
