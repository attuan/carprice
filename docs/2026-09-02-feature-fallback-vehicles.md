# 機能A の LLM フォールバックは Craigslist にそのまま移植できない

**日付**: 2026-09-02
**実装**: `scripts/run_feature_fallback.py --dataset {sienta,vehicles}`
**再現**: `.venv/bin/python scripts/run_feature_fallback.py --dataset vehicles --dry-run`
**結果**: `results/feature_fallback_vehicles.csv`
**関連**: `docs/2026-09-01-feature-fallback.md`（シエンタでの成功）/ PRD §6.1（機能A）/ §6.3（信頼度ルーティング）

---

## 何をしようとしたか

9/1 にシエンタで「確信度の低い15%だけ LLM に回すと正解率 0.873 → 0.942、
回した行は全問正解」という結果が出た（`docs/2026-09-01-feature-fallback.md`）。
**同じことが Craigslist の `model` でも成り立つか**を確かめようとした。

シエンタ側の課題の作りをそのまま移した。

| | シエンタ（成功した方） | Craigslist（この文書） |
|---|---|---|
| 入力 | `タイトル` | `model`（19,739種類の自由記述） |
| 正解 | 正規表現で抜いたグレード名（116水準） | `normalize_model()` の結果＝先頭2語（5,142水準） |
| 宣言値 | カタログを見て書ける10グレード | よく出る値の上位60個 |
| 採点 | fold1・test から400行 | fold1・test から400行（訓練48,000行） |

---

## 結果 — **測定として成立していない**

```
宣言した60値がカバーするのは test の 37.0%

 エスカレーション率  実際に回した行  accuracy  宣言値に限った accuracy
      0.00              0           0.370          1.000
      0.05              0           0.370          1.000
      0.15              0           0.370          1.000
      0.30              0           0.370          1.000
```

（`実際に回した行 0` はドライランのため。`QueueOnlyFallback` は答えずに
レビュー待ちへ積むだけなので、来歴の由来は `llm` ではなく `needs_review` になる）

**LLM を1回も呼ばない 0% の時点で、宣言値に限った accuracy が 1.000 に達している。**
つまり LLM が直せる行が1行も無い。この設計のまま本測定に進んでも、
費用を払って `+0.000` を確認するだけになる。

---

## なぜ成立しないのか

**正解を入力テキストの決定的な関数に取ってしまったから。**

`normalize_model()` は「区切り記号以降を捨てて先頭2語」という規則で、
正解は入力の部分文字列そのものになる。宣言値もその上位60個なので、
機能A がやっているのは文字 n-gram で `f-150 xlt supercrew` と `f-150` を
突き合わせる作業になり、近傍分類にとって自明な課題である。**迷う行が無いので、
「迷った行を LLM に回す」という仕組みを働かせる余地が無い。**

残りの 63% は宣言値の外にある 5,142 水準の裾で、こちらは逆に**どうやっても
正解にならない**。フォールバックのプロンプトは「候補のいずれか1つと完全に一致する
文字列を返す。勝手に新しい値を作らない」と指示しているので、
LLM が出す答えも必ず宣言した60値のどれかになる。したがって
**この課題の accuracy の上限はカバー率 37.0% で、それは 0% の時点ですでに達成されている。**
全体 accuracy 0.370 とカバー率 37.0% が一致するのはそのためである。

シエンタで成立したのは、グレード名がタイトルに書かれてはいるが**表記が揺れる**
（`G クエロ` / `Ｇ・クエロ` / `G Cuero`）ためで、揺れの吸収に近傍分類が迷い、
LLM が読めば解ける、という構図があった。Craigslist の `model` は
揺れる以前に正解がルールで機械的に決まってしまう。

---

## 何が分かったか

- **「人手ルールの結果を正解に取る」という測り方は、ルールが決定的な場合に使えない。**
  ルールが入力から一意に決まるなら、そのルールを近似する課題は自明になる。
  シエンタで使えたのは正規表現が表記揺れを吸収していた（＝決定的でなかった）ため。
- **正解の水準数とカバー率を先に見れば、測る前に気づけた。** 5,142 水準に対して
  宣言値60個ではカバー率が 37% しか無く、この時点で「上限が 37%」と分かる。
  今後この形の測定を作るときは、**宣言値のカバー率と、0% での accuracy を先に出す**。
- 費用は $0。ドライランで気づけたので、LLM は1回も呼んでいない。

---

## 測るならどうするか（未実施）

正解を**テキストから機械的に決まらない列**に替える。データ自身が持つ
`type`（ボディ形状）が候補になる。

| | この文書の測定 | 案 |
|---|---|---|
| 入力 | `model` | `model` |
| 正解 | `normalize_model(model)`（入力由来） | `type` 列（データが持つラベル） |
| 水準 | 5,142 | 13（sedan / SUV / pickup / truck / hatchback / coupe / wagon / van / convertible / mini-van / offroad / bus / other） |
| 難易度 | 部分文字列一致で自明 | `f-150 xlt supercrew` → `pickup` は世界知識が要る |

`type` は 24.5% 欠損なので、値のある行だけで採点することになる。
`unfold/demo.py` の `FeatureSpec` が `model` から `body_type` を作っているのも同じ発想で、
デモとも揃う。**ただしこれは「LLM が迷った行を直せるか」を測る話であって、
「`model` を13水準に潰した列が価格予測の役に立つか」は別問題**である。
後者は下流の MAE の話で、潰すこと自体は埋め込み（D4: 2,596 USD）に負ける。

---

## 測っていないこと

- **LLM を実際には1回も呼んでいない。** 上の議論は「フォールバックの答えも
  宣言値のどれかになる」という実装上の制約から導いた上限の話で、実測ではない。
- **下流の MAE は測っていない**（9/1 のシエンタ版と同じく）。
- `type` を正解にした案は**未実施**。
