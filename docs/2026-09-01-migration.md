# 計算ノードへの移行

**日付**: 2026-09-01
**対象**: `indx-internal-dev-us-east-1-attuan-compute`（`i-01b5d31ffbff67135`）
**手順書**: `dialogs/attuan-compute-node.html`（伊藤さん作）
**再現**: `scripts/sync_to_node.sh`

---

## なぜ移すか

決め手は CPU の速さではなく、**17時間のジョブをノートPCで走らせられない**こと。

`docs/2026-09-01-adaptive.md` の見積もりでは、6万行に機能B を素で当てると
$516・17時間かかる。この17時間はほぼ全部 API の応答待ち（1件あたり中央値 4.6 秒）で、
CPU は遊んでいる。**16コアにしても1秒も縮まない。**
それでも移すのは、手元の Mac の蓋を17時間開けっぱなしにできないからである。

副次的な効果は次の2つ。

- **CPU の実測が3〜5倍**。8/30 の夜間バッチは 00:03〜02:41 の2時間38分だった。
  コア数 6 → 16 に加えて世代が Coffee Lake（2018）から Sapphire Rapids（2023）に上がる
- **メモリ 16GB → 64GB**。CLAUDE.md が「pandas 全件読みで 6.8GB」と警告していた制約が消える
  （DuckDB を使う方針自体は変えない）

費用は稼働 $0.81/時。17時間のバッチを流して $13.8 で、同じジョブの API 費用 $516 の 2.7%。
手順書が「1日8時間×20日で $130」を通常の使い方として提示しているとおり、
**常用する前提で予算が組まれている**ので、節約のために使い控える必要はない。

| | 手元（i7-8850H） | 計算ノード（m7i.4xlarge） |
|---|---|---|
| コア | 6コア / 12スレッド | 16 vCPU |
| メモリ | 16 GB | 64 GB |
| OS | macOS | Ubuntu 24.04 |
| GPU | なし | なし |

GPU は付いていないが、既定エンコーダは文字 TF-IDF で torch を必須にしていないため
（`unfold/encoders.py`）、実質の不利はない。

## 全面移行にした理由

最初はハイブリッド（重いジョブだけノード）を検討したが、**やめた**。

ハイブリッドは、移行で最も避けたい事故を自分から作る構成だからである。

- **`llm_cache` が2か所に分かれる** → 同じ質問を2回買う
- **`sampledata/processed/` が2か所に分かれる** → 行の並びがずれて、
  位置で引く `load_dataset()` が別の行を返し、過去の測定と比較できなくなる

避けるべきは「全面移行」ではなく「**データの家が2つあること**」だった。
したがって `sampledata/` と、`results/` に数字を書くすべての実行はノードに寄せる。

手元の Mac に残す役割は2つだけ。**ネットが無いときの予備**と、
`unfold` はライブラリとして配るものなので**たまに macOS でも動くか確かめる**こと。

## 移送するもの / しないもの

git 管理下のものは clone すれば済む。問題は git 管理外の 631MB。

| 対象 | 扱い | 理由 |
|---|---|---|
| `processed/llm_cache/`（18MB） | **転送** | 置いていくと同じ質問を買い直す |
| `processed/*_clean.parquet` | **転送** | 行の並びを保つ。再生成に賭けない |
| `processed/*_emb_*.parquet`（97MB） | **転送** | `.venv-embed`（torch）の再構築が要るため転送が安い |
| `processed/vehicles_multi_withdup.parquet`（324MB） | 任意 | `clean_vehicles.py` で再生成できる |
| `raw/vehicles.csv`（1.4GB） | **転送しない** | Kaggle から直接取り直す方が速い |
| `.venv` / `.venv-embed` | **転送しない** | Linux の wheel は別物。コピーしても動かない |
| APIキー | **転送しない** | ノード側で `.env.example` から作り直す |

## 移行後の検証（同じ測定を両環境で回した）

`vehicles_multi_clean.parquet` を移送したあと、同じ 60,000 行・5-fold を両方で回した。

| | 手元（Mac / 12論理コア） | ノード（Ubuntu / 16 vCPU） | |
|---|---:|---:|---|
| 抽出行の指紋 | 947663996.0000 | 947663996.0000 | 一致 |
| A2 LightGBM・構造化列 MAE | 3229.936 ± 12.887 | 3229.936 ± 12.887 | **完全一致** |
| C2 ＋車種名の文字TF-IDF MAE | 2616.960 ± 24.397 | 2619.035 ± 22.391 | **2.08 のズレ** |
| A2 の所要 | 9.6 秒 | 5.7 秒 | 1.7 倍 |
| C2 の所要 | 70.1 秒 | 31.8 秒 | 2.2 倍 |
| データ読み込み | 1.9 秒 | 0.7 秒 | 2.7 倍 |
| テスト 104 件 | 34.1 秒 | 22.3 秒 | 1.5 倍 |

**ズレの原因は LightGBM のバイナリ差である。** 切り分けの手順は次のとおり。

1. **データは同一。** parquet 11 本と `llm_cache` 3,809 ファイルは
   SHA-256 で全件一致。抽出された 60,000 行の指紋も一致
2. **スレッド数ではない。** `n_jobs=4` + `deterministic=True` + `force_row_wise=True`
   に固定しても値は動かなかった。**各機は自分の中では完全に決定的**で、
   機械をまたぐときだけズレる
3. **TF-IDF でもない。** 60,000 × 1,000 の疎行列を両環境で作って比べたところ、
   語彙・非ゼロ数・値のバイト列ハッシュがすべて一致した
4. 残るのは LightGBM 自身。**A2（13列）は完全一致で C2（1,013列）だけズレる**のは、
   列が増えるほど浮動小数点の集約回数が増えるため。Coffee Lake（AVX2 / Apple clang）と
   Sapphire Rapids（AVX-512 / gcc）では和の順序が変わり、まれに分割点が変わる

**実害の大きさ。** ズレは 2.08、率にして **0.079%**。同じ測定の fold 間のばらつき
（MAE_std 22〜24）や、`docs/2026-08-30-overnight.md` で確認した振れ幅（±6〜16）より
**1桁小さい**。既存の結論を覆すものではない。

**ただし、機械をまたいだ数値を同じ表に並べてはいけない。** `results/leaderboard*.csv`
の既存の行はすべて Mac で測ったものなので、ノードで測り直すと僅かに動く。
これは**測定機を1つに寄せる根拠がもう1つ増えた**ということでもある。

宿題として、(a) leaderboard に実行環境の列を足す、(b) 主要な行をノードで測り直して
記録を揃える、の2つが残る。

## 運用上の注意

**自動停止に引っかかる。** ノードは CPU 使用率 5% 未満が1時間続くと自動で落ちる。
**LLM のバッチはまさにこれに該当する** — API の返事を待っているだけなので、
16 vCPU に対して 0.2 コア分も使わない。何もしなければ1時間後に確実に殺される。
コードを読んでいる時間など、対話作業の低負荷時間も同様。
**しきい値の引き上げを伊藤さんに依頼すること。**

**止め忘れは月 $589。** 作業を終えたら必ず停止する。

```bash
aws ec2 stop-instances --instance-ids i-01b5d31ffbff67135
aws ec2 describe-instances --instance-ids i-01b5d31ffbff67135 \
  --query 'Reservations[0].Instances[0].State.Name' --output text   # stopped を確認
```

**`terminate` は使わない。** ディスクごと消えて戻らない。止めるのは常に `stop`。
